## [medium] behaviour-01: Dark mode: the focus outline on the divider tabs (desktop and mobile) is #1c1b19 drawn on the dark desk, so it can barely be seen (about 1.05:1)
- file: src/components/Desk.module.css:18 (checklist gl-24 / bh-12)
- expected: README 'Keyboard focus: add a visible outline:2px solid #1c1b19; outline-offset:2px'. The site already treats controls that sit on the desk differently in dark mode: Desk.module.css:18-20 switches the header controls' outline to var(--desk-ink-dark) because a #1c1b19 ring does not show on the dark desk. The divider tabs also sit on the desk. The desktop tabs stick out past the right edge of the paper, and the mobile row sits above the pile. So in dark mode they need an outline that can be seen, just like the header controls.
- actual: The dark override is limited to `.header :focus-visible`. Tab buttons (Tabs.module.css .tab at line 9 and .tabMobile) fall back to the global `:focus-visible { outline: 2px solid var(--ink) }` rule (globals.css:113), which gives rgb(28,27,25) in dark mode. Because of the 2px offset, the ring is drawn on the desk and not on the tab's own coloured background. In dark mode a keyboard user cannot see which tab has focus.
- fix: In src/components/Tabs.module.css add: `:global([data-desk='dark']) .tabsDesktop :focus-visible, :global([data-desk='dark']) .tabsMobile :focus-visible { outline-color: var(--desk-ink-dark); }` (mirroring Desk.module.css:18). Add an e2e test in dark mode that focuses a desktop tab at 1440px and a mobile tab at 390px and expects outlineColor rgb(232, 228, 220).

## [low] behaviour-02: Reduced motion: bring() still smooth-scrolls to the top, because the JS forces behavior:'smooth' and so overrides the reduced-motion CSS
- file: src/lib/usePile.ts:164 (checklist bh-13 / bh-04)
- expected: With prefers-reduced-motion: reduce, globals.css:84-88 sets `html { scroll-behavior: auto }` so the page does not scroll with an animation. bh-13/README: under reduced motion, swaps are instant (the slide is replaced by a cross-fade). The scroll-to-top that bring() performs when scrollY > 80 should therefore jump, not animate.
- actual: useBring calls `window.scrollTo({ top: 0, behavior: 'smooth' })` without checking the preference. An explicit `behavior: 'smooth'` overrides the CSS scroll-behavior, so under reduced motion the page still scrolls with an animation of about 300ms.
- fix: In src/lib/usePile.ts:164 change to `window.scrollTo({ top: 0, behavior: reducedMotion ? 'auto' : 'smooth' });`. Extend the bh-04 unit test in usePile.test so that with reducedMotion=true it asserts scrollTo is called with behavior 'auto'.

To also stop it covering the text, either log the 560-640px overlap as an accepted deviation in docs/implementation-notes.md next to the name/tagline note, or add a media query for (min-width:600px) and (max-width:640px) plus the 560-599 mobile band that moves the note clear (e.g. a smaller `top`/`right` offset). Add an e2e test at 560px that asserts elementFromPoint over the right end of the GitHub link returns the link.

## Refuted

Result: the URL is 'http://localhost:5205/' and the title is 'Ali Bars', so the CV is on top. The code path matches the finding: usePile.ts onHashChange queues into pendingRef only when moving !== null, and canBring (pile.ts:112-114) rejects anything while phase !== 'done'. This is not a defect, though. The requirement it cites, docs/acceptance-checklist.md:258 extra-bh-21, says a hashchange brings the matching sheet 'respecting bring() guards', and canBring's first guard is that the intro is done. So ignoring a hash edit during the intro is exactly the behaviour the checklist allows. It keeps the URL in step with the sheet that is actually on top, so the address bar does not claim #racing while the CV shows. code-r2-02 was a different case: a mid-move Back caused a pushState that truncated forward history and put the pile on the wrong sheet. Here no forward history is lost and the URL is not left out of step with the pile. Queuing hash edits made during the intro would be an enhancement beyond the spec, not a fix.
